# Init Requires Installed Provider CLI

`aio init` and `aio setup` must not scaffold `.aio/` until the machine has at
least one runnable provider CLI that aio can wire up without hand-editing
`.aio/providers.yaml` first.

Init probes known provider commands (see `PROVIDER_PROBE_CATALOG` in code): each
entry runs `command` + `args` (typically `--version`) and treats exit code `0`
as detected. Detected providers are listed for the user.

When stdin and stdout are TTYs and **more than one** provider passes the probe,
the user **chooses** which provider is the default for roles and workflows.
When only one passes, init prints what was detected and uses it without an
extra prompt. Non-interactive runs use the **first** detected provider in probe
catalog order, unless overridden by `AIO_DEFAULT_PROVIDER` (must match a
detected id) or by programmatic `defaultProvider` / test hooks.

`.aio/config.yaml` records the choice under `defaults.provider`.

If no probe succeeds, the command fails with a clear error. The message
explains that aio needs a local LLM provider CLI, points to installing supported
CLIs when applicable, and mentions configuring the `custom` entry (or another
provider block) in `.aio/providers.yaml` after the user can invoke a CLI on their
system.

New role files bind to the chosen provider so the default workflow can execute
against the configured command instead of defaulting to an unconfigured `custom`
role.

Tests may inject `probeProvider`, `probeProviders`, or `defaultProvider` so
automated runs do not depend on a real CLI install.
